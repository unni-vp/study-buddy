Subroutines

Subroutines and structured programming

A subroutine is a named block of code called from elsewhere.

FeatureProcedureFunction
Main purposeCarries out a task without returning a useful result to the caller.Calculates and returns a value to the calling code.
ExampleDisplay a menu.Calculate a rectangle’s area.
Using the resultCall it to perform the action.Use its returned value in an expression or assignment.

Python uses def for both styles of subroutine.

  • A parameter passes data into a subroutine.
  • A return value passes a result out.
  • A local variable exists only while its subroutine runs and is accessible only there.

Advantages include reuse, less repeated code, easier testing, easier maintenance and clearer decomposition.

Structured programming builds a program from small modules with clear interfaces. Parameters, local variables and return values reduce unwanted dependence between modules.

Passing values in and returning a result

def rectangle_area(width, height):
    area = width * height
    return area

first_area = rectangle_area(4, 6)
print(rectangle_area(3, 5))

width and height are parameters. The first call supplies 4 and 6 as arguments, so first_area receives 24. The second call supplies different values and prints 15.

return sends a result back to the caller and ends that function call. Printing displays text but does not provide the same returned result. A returned value can be assigned, passed to another call or used directly in an expression.

The local area belongs to the function call. Code outside the function should use the returned value rather than try to read area directly. Local names help prevent one module accidentally changing another module's working data.

Why structure helps

A reusable function can replace several copies of the same calculation. One correction then fixes every call, instead of leaving slightly different copies to maintain. Each module can be tested separately with known inputs and expected outputs.

Clear parameters and return values state what a module needs and provides. They also let different programmers develop separate modules, provided those interfaces agree.

Documenting a clear interface

An interface tells the caller how to use a subroutine. It is like the order instructions on a takeaway menu: the caller needs to know what to supply and what comes back, without following every step in the kitchen.

For rectangle_area(width, height), useful documentation states:

Part of the interfaceWhat the caller needs to know
Name and purposerectangle_area calculates a rectangle's area.
Parameters and orderSupply width first, then height, as numeric values in the same length unit.
AssumptionsThis calculation expects non-negative dimensions. It does not itself validate them.
Return valueThe returned number is the area in square units. It is not automatically displayed.

Parameter order matters when the calculation is not symmetrical. A function defined as subtract(first, second) and returning first - second gives 6 for subtract(10, 4), but −6 for subtract(4, 10).

Comments should explain purpose, assumptions or a difficult choice. A comment such as “The upper limit is excluded by range” can clarify a loop. Repeating “add one” beside an obvious addition adds little. Update comments when the code changes.

Local variables keep a module's working data separate. A value that many unrelated modules can change creates a shared dependency: a change elsewhere can unexpectedly affect the result. Passing needed values in and returning a result makes that relationship easier to follow.

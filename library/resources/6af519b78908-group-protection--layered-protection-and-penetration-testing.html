Protection and testing

Layered protection and penetration testing

Use measures together

No single measure addresses every threat.

  • A strong password is useful against guessing, but can still be disclosed during phishing.
  • Training and independent identity checks reduce social-engineering risks.
  • Updates and anti-malware reduce technical risks.
  • Appropriate access rights limit what an account can do.

Combining measures protects different weak points, like having a lock, a visitor check and a working alarm rather than relying on one door alone.

Penetration testing

Penetration testing is an authorised, controlled attempt to find security weaknesses by testing how an attacker might gain access. Its purpose is to discover problems so they can be fixed.

Test situationWhat the testers knowWhat it helps reveal
Insider simulationSome knowledge of the system, and possibly ordinary user credentialsWhether an insider can exceed their intended permissions or exploit internal weaknesses
External simulationNo prior knowledge of access credentialsHow someone outside the system might gain unauthorised access

A test report identifies weaknesses, their consequences and recommended fixes. The organisation should correct the weaknesses and retest. Testing finds problems; it does not itself repair them.

Detection, prevention and recovery

JobExampleWhy the distinction matters
PreventionInstalling a patch closes a known vulnerability.This reduces an attack route before it is exploited.
DetectionAnti-malware identifies a suspicious file.Finding a threat allows action, but detection alone is not the same as preventing every infection.
RecoveryA protected backup restores damaged records.Restoring files does not undo confidential data already stolen.

An insider-style test can explore what an ordinary account can reach beyond its intended permissions. An external-style test starts without credentials and investigates access from outside. Both need agreed authorisation and scope.

From a test finding to a safer system

Suppose an authorised tester using an ordinary staff account can delete payroll records:

StageWhat should happen?
Agree the testDefine which systems and actions are permitted so the test is controlled.
Record the findingExplain that the account has excessive permissions and show the possible consequence.
Correct the weaknessRestrict deletion rights to the roles that need them. Changing the password alone does not fix this permission.
RetestCheck that ordinary staff can no longer delete the records and that authorised payroll work still functions.

A successful test of one route is not proof that every other route is secure. Review the findings, apply fixes and continue maintaining the system.
